## 1. 성능 목표

| 우선순위 | 항목 | Phase 1 (Local PC · 파일 기반) | Phase 2 (RTSP 에뮬레이터) | Phase 3 (Jetson · 실 카메라) |
|:---:|---|:---:|:---:|:---:|
| 1 | Re-ID Rank-1 정확도 | **≥ 70%** | **≥ 80%** | **≥ 80%** |
| 2 | Re-ID mAP ² | **≥ 45%** | **≥ 60%** | **≥ 55%** |
| 3 | False Negative (재인식 실패) ¹ | **≤ 20%** | **≤ 12%** | **≤ 15%** |
| 4 | False Positive (오인식) | **≤ 5%** | **≤ 5%** | **≤ 5%** |
| 5 | ID Switching | **≤ 5%** | **≤ 5%** | **≤ 5%** |
| 6 | FPS | — | — | **45~60 FPS** (3채널 합산) |
| 7 | 벡터 검색 응답 | — | — | **50ms 이내** |
| 8 | 대시보드 갱신 | — | — | **500ms 이내** |
| 9 | 가용성 | — | — | **99% 이상** |

### 1.1 목표치 설정 근거

| 항목 | 근거 |
|---|---|
| **Re-ID Rank-1** | OSNet-x0.25 벤치마크(Market-1501) 84% 기준. 실환경 도메인 시프트로 15~25%p 하락이 전형적이므로 80%는 도전적이지만 파인튜닝 시 달성 가능한 수준. Phase 1 목표 70%는 임계값 조정만으로 달성 가능한 중간 기준 (실측 71.0%). |
| **Re-ID mAP** | OSNet-x0.25 벤치마크 mAP ~60%. Rank-1 대비 20%p 내외 낮은 것이 전형적이며 실환경에서는 격차가 더 벌어짐. Phase 1 목표 45%는 추정치이므로 실측 후 재조정 필요. |
| **False Negative** | 임계값 0.73 적용 후 실측 17.9%로 Phase 1 목표 이미 달성. SOTA 실환경 수준 ~10%에 근접하는 것이 Phase 2 목표. SS-01(실종자 추적) use case에서는 FN이 낮을수록 치명적 누락을 줄임. Phase 3는 RTSP 열화(-3~8%p) 감안해 완화. |
| **False Positive** | 현재 실측 0.0% — 이미 달성. 임계값 0.73이 FN·FP 합산 오류를 최소화하는 균형점. 보안 use case에서 오인식은 신뢰도에 치명적이므로 5% 기준은 엄격하게 유지. |
| **ID Switching** | 실측 0.0~0.08% — PRD 목표 5% 대비 크게 초과 달성. ByteTrack이 저신뢰도 탐지까지 활용해 ID 연속성이 우수. 5%는 업계 일반 기준이며 현재 구성에서 리스크 없음. |
| **FPS** | 3채널 × 카메라 스펙 15~20 FPS = 합산 45~60 FPS. Jetson Orin Nano에서 TensorRT FP16 적용 시 달성 가능하나 현재 미검증 (Todo). Phase 1~2는 Local PC 환경이므로 해당 없음. |
| **벡터 검색 50ms** | pgvector HNSW 인덱스 기준 10,000건 기준 목표. 인덱스 없는 전수 탐색은 데이터 증가 시 수 초 소요. HNSW 인덱스 사전 생성으로 달성 가능 (Action Item 1-8). |
| **대시보드 갱신 500ms** | 사람이 "즉각적 반응"으로 인식하는 응답 상한선. WebSocket 또는 HTTP Polling(3~5초 주기)으로 달성 가능하며, 서버·DB 성능이 병목이 아닌 한 구현 난이도 낮음. |
| **가용성 99%** | 연간 약 87시간 이하 다운타임 허용 수준. RTSP 자동 복구 + Docker `restart: always` + SQLite 오프라인 버퍼 조합으로 달성 가능. Jetson 하드웨어 장시간 안정성 검증(Action Item 3-4) 필요. |

### 3.6 Action Item 보충 설명

#### 3.6.1 Phase 1

**1-1. `.env` REID_SIMILARITY_THRESHOLD=0.73 적용**
* 현재 임계값 0.85는 너무 엄격해 같은 사람을 새 사람으로 판단하는 FN율이 39.4%에 달한다.
* 노트북 실측 결과 0.73이 FN+FP 합산 오류를 최소화하는 최적값으로 도출됐다.
* `.env` 파일 한 줄 변경으로 FN율을 17.9%로 낮추고 Rank-1을 61.5%→71.0%로 즉시 개선할 수 있다.
* 영상마다 최적값이 0.70~0.77로 다르므로 적용 후 결과를 노트북으로 재확인하는 것이 좋다.

**1-2. 화질 게이트 (라플라시안 분산 기반)**
* 라플라시안 필터로 프레임의 선명도 점수를 계산해, 일정 임계값 미만의 흐릿한 프레임은 Re-ID 추출을 건너뛴다.
* 네트워크 압축 아티팩트나 모션 블러로 오염된 프레임이 임베딩 품질을 저하시키는 것을 방지한다.
* `cv2.Laplacian(frame, cv2.CV_64F).var()`로 20줄 이내 구현 가능하며, `ImagePreprocessor` 또는 `ReIDExtractor` 호출 직전에 삽입한다.

**1-3. Temporal Mean Pooling 구현**
* 동일 Track ID의 체류 기간 동안 추출된 복수의 Re-ID 벡터를 단순 평균(Mean Pooling)하거나
* YOLO 신뢰도 가중 평균(Confidence-weighted Pooling)으로 합산해 단일 고품질 벡터를 생성한다.
* 단일 프레임 벡터는 포즈·조명 노이즈에 취약하지만, 평균 벡터는 이를 통계적으로 상쇄한다.
* `BestShotSelector`에 누적 벡터 목록을 유지하다가 트랙 소멸 시 평균을 전송하도록 수정한다.

**1-4. Re-ID 전용 큐 분리**
* 현재 `ThreadedPipelineRunner`는 실시간성을 위해 프레임 큐 크기를 1~2로 유지하며 최신 프레임만 처리한다.
* 이 전략은 화면 표시에는 적합하지만 Re-ID Best-shot 후보 프레임이 드롭되는 문제를 일으킨다.
* 표시용 큐(크기 1~2)와 Re-ID 추출용 큐(크기 5~10)를 분리해, 표시는 최신 프레임만 유지하되 Re-ID는 더 많은 후보를 평가할 수 있게 한다.

**1-5. `max_missing_frames` 값 튜닝**
* `BestShotSelector`의 `max_missing_frames`는 객체가 연속 몇 프레임 동안 미검출될 때 소멸로 판정할지 결정한다.
* 기본값 30프레임(약 1~2초)은 RTSP 재연결 시간보다 짧을 수 있다.
* 재연결 예상 시간(예: 3~5초 → 75~125프레임)에 맞게 값을 늘리면 짧은 끊김 후 재연결 시 동일 Track ID를 유지할 수 있다.

**1-6. OSNet 모델 Lifespan 캐싱 구현**
* 현재 서버의 이미지 검색 API는 호출마다 OSNet 모델을 로드하는 구조로, 응답 지연이 수 초에 달할 수 있다.
* FastAPI의 `lifespan` 이벤트(startup)에서 OSNet 모델을 RAM/VRAM에 1회 로드하고 전역 상태로 유지하면,
* 이후 API 호출은 모델 로딩 없이 즉시 임베딩 추출이 가능하다. `server/models/osnet_x0_25.onnx` 경로는 에지와 동일한 가중치를 참조해야 한다.

**1-7. 서버 이미지 검색 API 구현 (`POST /v1/search/identity`)**
* 관리자가 웹 대시보드에서 인물 이미지를 업로드하면 서버가 OSNet으로 임베딩을 추출하고 pgvector DB와 코사인 유사도를 비교해 해당 인물의 과거 이력을 반환하는 API다.
* 입력은 `.jpg`/`.png` 멀티파트 폼, 출력은 유사도 상위 K건의 카메라 ID·타임스탬프·스냅샷 경로 목록이다.
* 1-6의 Lifespan 캐싱이 완료된 후 구현해야 응답 속도가 보장된다.

**1-8. pgvector HNSW 인덱스 생성**
* pgvector는 인덱스 없이도 정확한 코사인 유사도 검색이 가능하지만, 데이터가 수만 건을 넘으면 전수 탐색(Brute-force) 방식으로 인해 응답 시간이 급격히 증가한다.
* HNSW(Hierarchical Navigable Small World) 인덱스를 사전에 빌드해두면 10,000건 기준 50ms 이내 검색이 가능해진다.
* `CREATE INDEX ON events USING hnsw (vector vector_cosine_ops);` 한 줄로 생성하며, 인덱스 빌드는 데이터 적재 전 수행하는 것이 권장된다.

**1-9. 실시간 데이터 바인딩 (WebSocket / HTTP Polling)**
* 현재 대시보드 차트는 정적 데이터를 표시한다.
* WebSocket 또는 주기적 HTTP Polling을 추가해 에지에서 전송되는 실시간 입/퇴장 카운트와 체류 시간 통계를 차트에 즉시 반영한다.
* 구현 난이도가 낮은 HTTP Polling(3~5초 주기)으로 먼저 구성하고, 이후 WebSocket으로 전환하는 것이 안전하다.

**1-10. 이미지 검색 업로드 위젯 구현**
* 1-7의 서버 API와 연동하는 프론트엔드 컴포넌트다.
* Drag & Drop으로 인물 이미지를 업로드하면 `POST /v1/search/identity`를 호출하고, 반환된 이력(카메라·시간·스냅샷)을 카드 형태로 표시한다.
* React의 `react-dropzone` 라이브러리를 활용하면 빠르게 구현 가능하다.

**1-11. 노트북 mAP 평가 구현**
* mAP(mean Average Precision)는 Rank-1과 함께 Re-ID 성능의 완전한 그림을 제공하는 표준 지표다.
* Rank-1이 "1위 매칭의 정확성"을 보는 반면, mAP는 "한 인물의 모든 출현을 얼마나 빠짐없이 찾는가"를 측정하므로 SS-01(실종자 전수 조사) use case에서 특히 중요하다.
* 구현 방법: `results/*.pkl`의 트랙 임베딩을 gallery/query로 절반씩 분리하고 `average_precision_score`로 per-query AP를 계산한 뒤 평균을 낸다.
* Phase 1 목표(≥45%)는 추정치이므로, 실측 기준값에 따라 Phase 2/3 목표를 재조정한다.

**1-12. YOLO 탐지율 간접 진단**
* GPU 재실행 없이 기존 `results/*.pkl`만으로 YOLO 탐지 품질을 간접 평가하는 분석이다.
* **단명 트랙 비율**: 생존 프레임 수 < 10인 트랙이 전체 트랙 수의 몇 %인지 확인한다. 이 비율이 30% 이상이면 탐지 누락(사람이 있지만 bbox 없음) 또는 ID 분열이 빈번하다는 신호다.
* **frag_pairs 수**: 동일인 의심 트랙 쌍(`frag_pairs`)의 수가 많을수록 한 사람이 여러 트랙으로 쪼개지는 탐지 불연속이 잦다는 뜻이다.
* **bbox 면적 분포**: `thumbnail` 크기나 bbox 좌표 기반으로 탐지된 인물 크기 분포를 히스토그램으로 확인한다. 매우 작은 bbox(< 32×64 px)가 많으면 해상도 대비 탐지 거리가 지나치게 멀거나 모델 해상도 한계에 도달한 것이다.
* 진단 결과에 따라 YOLOv8n → YOLO11n 교체, CrowdHuman 가중치 교체, 입력 해상도 조정 등 개선 방향을 결정한다 (Section 4.1 참조).
* 노트북 내 별도 진단 셀로 구현하거나 `reid_aggregate.ipynb`에 추가한다.

**1-13. 추적기 품질 진단 (MOT 간접 진단)**
* 기존 `results/*.pkl`의 `track_quality` 딕셔너리를 분석해 ByteTrack 추적기의 성능을 간접 진단한다.
* **주요 지표**:
  - `switch_rate`: 트랙 내 임베딩 급변 비율 (높을수록 ID 스위칭 또는 별개 인물 혼입 의심)
  - `mean_sim` / `min_sim`: 트랙 내 평균·최솟값 임베딩 유사도 (낮을수록 트랙 순도 저하)
  - `n_switches`: 임계값 기반 의심 전환 횟수 (직접적인 ID 스위칭 카운트)
* **분석 방법**: `switch_rate > 0.1` 또는 `mean_sim < 0.6` 인 트랙을 이상 트랙으로 분류하고, 전체 트랙 중 비율을 계산해 추적기 품질을 수치로 표현한다.
* **한계**: `track_quality`는 임베딩 기반 proxy 지표이므로 Re-ID 모델의 품질과 혼합 측정된다. Re-ID 모델과 추적기 성능을 완전히 분리하려면 수동 라벨링 기반 MOTA/IDF1 측정이 필요하다 (Phase 2 Action Item 2-6 참조).
* 진단 결과에 따라 `max_missing_frames` 튜닝(Action Item 1-5), ByteTrack → OC-SORT 전환(Section 4.2) 등 개선 방향을 결정한다.

#### 3.6.2 Phase 2

**2-1. Mediamtx 에뮬레이터 3채널 동시 RTSP 스트림 테스트**
* Mediamtx 인프라는 이미 구축(Done)됐다.
* 이제 실제 영상 파일 3개를 동시에 RTSP로 송출하고, `MultiStreamPipelineRunner`가 3채널을 안정적으로 수신·처리하는지 확인하는 테스트를 수행한다.
* 네트워크 지연과 패킷 손실을 `tc netem`으로 인위적으로 주입해 RTSP 환경에서의 성능 열화를 측정한다.

**2-2. I-프레임 우선 Re-ID 추출**
* H.264/H.265 스트림에서 P/B 프레임은 이전 프레임 차분으로 구성돼 블로킹 아티팩트가 심하다.
* GStreamer 파이프라인 또는 OpenCV 프레임 메타데이터에서 I-프레임 여부를 감지하고, Re-ID 추출을 I-프레임에 우선 할당한다. 2-1 테스트와 병행해 Rank-1 변화를 측정한다.

**2-3. 실환경 데이터 수집**
* 도메인 파인튜닝(2-4)의 전제 조건이다.
* 실제 카메라가 설치될 공간(또는 유사 환경)에서 다양한 조명·의상·각도로 10~30명을 촬영해 Re-ID 학습 데이터를 구성한다.
* 인물당 최소 6개 카메라 뷰(2개 카메라 × 3회 이상 재방문) 이상 확보해야 파인튜닝 효과가 나타난다.
* 데이터 수집량이 적을수록 파인튜닝 효과가 제한적이므로 최대한 다양한 조건에서 수집한다.

**2-4. osnet_x0_25 도메인 파인튜닝**
* 2-3에서 수집한 실환경 데이터로 osnet_x0_25를 추가 학습한다.
* Torchreid의 `ImageDataManager`와 `Engine`을 사용하면 기존 코드 구조를 크게 바꾸지 않고 파인튜닝이 가능하다.
* Triplet Loss 또는 ID Loss + Triplet Loss 조합이 Re-ID에 효과적이다.
* 파인튜닝 전후 노트북으로 Rank-1을 재측정해 효과를 정량화하고, 개선이 미미하면 osnet_x1_0 파인튜닝(조합 #16)으로 전환을 고려한다.

**2-5. 영상별 적응형 임계값**
* 단일 고정 임계값(0.73)은 영상마다 최적값이 0.70~0.77로 다른 상황에서 차선책이다.
* 카메라별로 `.env`에 별도 임계값 변수(`REID_THRESHOLD_CAM01`, `REID_THRESHOLD_CAM02` 등)를 두거나,
* 초기 구동 시 짧은 캘리브레이션 구간에서 intra/inter 유사도 분포를 자동 측정해 최적값을 계산하는 자동 보정 로직을 구현한다.

**2-6. 짧은 클립 수동 라벨링 + MOTA/IDF1 측정**
* 50~100명 규모의 영상 클립(5~10분)에 BBox + 인물 ID를 수동 라벨링하고
* `py-motmetrics` 라이브러리로 MOTA, IDF1, IDsw를 측정한다.
* 현재 노트북의 임베딩 기반 proxy 지표와 달리, 이 지표는 Re-ID 모델의 영향을 받지 않는 순수한 추적기 성능값이다. Phase 2 파인튜닝 전후 추적기 성능 변화도 함께 확인한다.

**2-7. 이벤트 트리거 전송 구현 (Enter/Exit/Line Crossing)**
* 현재는 Best-shot 선별 후 트랙 소멸 시 전송하는 방식이다.
* 진입(Enter), 가상 카운팅 라인 통과(Line Crossing), 퇴장(Exit) 등 비즈니스 이벤트 시점에만 선택적으로 전송하면 서버 수신 부하를 크게 줄일 수 있다.
* `AnalyticsEngine`의 `counting_line_y` 로직을 확장해 이벤트 상태를 관리하고, 해당 시점에만 `http_sender`를 호출하도록 수정한다.

**2-8. 다채널 병렬 처리 완성 (MultiStreamPipelineRunner)**
* 현재 `MultiStreamPipelineRunner` 클래스는 설계는 돼 있으나 실제 RTSP 환경 테스트가 미완이다.
* 채널당 디코딩 스레드가 독립적으로 동작하고 단일 GPU 추론 인스턴스를 공유하는 구조를 검증한다.
* 채널 간 프레임 타이밍 충돌로 인한 GPU 락 경합 여부와 OOM 발생 여부를 2-1 테스트 환경에서 집중 검증한다.

**2-9. SQLite 오프라인 버퍼 + Batch Flush 데몬**
* 네트워크 단절 시 추출된 벡터·스냅샷 데이터를 로컬 SQLite 큐에 임시 저장하고, 재연결 후 서버 벌크 API(`POST /v1/events/bulk`)로 병렬 전송하는 백그라운드 데몬을 구현한다. 전송 성공한 레코드만 SQLite에서 삭제(트랜잭션 보장)하고, 재전송 시 타임스탬프 순서를 보존해 서버 통계 정합성을 유지한다.

**2-10. 네트워크 장애 모의 E2E 테스트**
* `tc netem`으로 에지-서버 간 네트워크를 인위적으로 차단(drop 100%)한 뒤 일정 시간 후 복구하고, SQLite 적재 → 복구 감지 → Batch Flush 순서가 데이터 유실 없이 동작하는지 검증한다. 장애 전후 서버 DB 레코드 수와 에지 SQLite 잔여 레코드 수를 비교해 정합성 100%를 확인한다.

**2-11. 보행자 동선 타임라인 위젯**
* 특정 Global ID(또는 이미지 검색 결과)에 대해 "CAM_01 → 09:12 → CAM_03 → 09:15 → CAM_02 → 09:18" 형태의 시간순 동선을 시각화하는 타임라인 컴포넌트를 구현한다. `GET /v1/events?global_id=X` API 응답을 파싱해 카메라별 스냅샷과 타임스탬프를 가로 타임라인으로 렌더링하며, 동선 타임라인은 1-10의 이미지 검색 결과와 연동된다.

**2-12. 카메라 교차 매칭 임계값 튜닝**
* 단일 카메라 내 Re-ID와 달리 카메라 간 교차 매칭은 조명·각도 차이로 인해 유사도가 낮게 나온다. 서버의 `matcher.py`에서 사용하는 크로스 카메라 코사인 유사도 임계값을 단일 카메라 임계값(0.73)보다 낮게 조정하거나, 카메라 쌍별로 별도 임계값을 `.env`에서 관리한다. 2-6의 MOTA/IDF1 측정과 함께 교차 매칭 성능을 정량적으로 평가한다.

#### 3.6.3 Phase 3

**3-1. YOLOv8n TensorRT FP16 엔진 변환 및 FPS 측정**
* Jetson에서 `yolov8n.pt`를 TensorRT FP16 `.engine` 파일로 변환한다. 변환은 최초 실행 시 자동으로 이루어지지만, 변환 시간(수 분)을 배포 전 미리 완료해두는 것이 권장된다. `.engine` 파일은 빌드한 Jetson 보드에 종속되므로 다른 장비로 복사 불가하다. 변환 후 단일 채널 FPS를 측정해 15 FPS 이상 달성 여부를 확인한다.

**3-2. OSNet ONNX Runtime CUDA 가속 검증**
* Jetson에 `onnxruntime-gpu` 패키지를 설치하고 `CUDAExecutionProvider`로 OSNet 추론 속도를 측정한다. CPU 대비 4~6배 속도 향상이 예상되며, 이를 달성하지 못하면 Re-ID 추출이 전체 파이프라인의 병목이 된다. ONNX 파일은 에지와 서버가 동일한 `osnet_x0_25.onnx`를 참조해야 임베딩 벡터 분포가 일치한다.

**3-3. 3채널 동시 실행 FPS 벤치마크**
* 3-1, 3-2 완료 후 `MultiStreamPipelineRunner`로 3채널을 동시 실행하며 합산 FPS를 측정한다. 목표는 45 FPS 이상(채널당 15 FPS)이며, GPU 공유 구조로 인해 단일 채널 FPS의 3배에 미치지 못할 수 있다. 병목이 GPU 추론인지 디코딩인지를 `jtop`으로 프로파일링해 원인을 파악한다.

**3-4. 장시간 안정성 테스트 (jtop 모니터링)**
* 3채널 동시 실행 상태에서 최소 1~2시간 연속 가동하며 GPU/CPU 사용률, VRAM 점유량, 코어 온도를 `jtop`으로 기록한다. OOM(Out of Memory) 발생, 온도 임계값 초과로 인한 스로틀링, 메모리 누수에 의한 점진적 성능 저하를 점검한다. Jetson Orin Nano의 TDP는 7~15W이며 팬리스 케이스 사용 시 과열 리스크가 있다.

**3-5. 실 IP 카메라 RTSP 스트림 연결 및 화질 확인**
* 실제 IP 카메라를 Jetson과 동일 LAN에 연결하고 RTSP URL로 스트림을 수신한다. 카메라 비트레이트(최소 2Mbps 권장), 해상도(1080p), 프레임레이트(15~20 FPS), 코덱(H.264 권장) 설정을 확인하고 최적화한다.

**3-6. 실환경 RTSP 기반 Rank-1 재측정**
* Phase 2 파인튜닝 모델을 탑재한 상태에서 실 IP 카메라 스트림으로 Rank-1 정확도를 측정한다. 로컬 파일 기반 수치(Phase 2 목표 80%)보다 5~13%p 낮을 것으로 예상되므로, 실환경 기준 목표치를 별도로 설정하는 것이 필요하다. 결과에 따라 임계값 재조정 또는 추가 파인튜닝 여부를 결정한다.

**3-7. Docker 컨테이너 빌드 (Jetson Native Build)**
* 베이스 이미지는 `nvcr.io/nvidia/l4t-pytorch` (ARM64 전용)이며, x86 호스트 PC에서 빌드한 이미지는 사용 불가하다. `docker compose up -d`로 Qdrant와 파이프라인을 함께 기동하며, 재부팅 후 자동 실행(`restart: always`) 설정을 포함한다.

**3-8. `manage_stream.sh` 연동 및 프로덕션 실행 검증**
* 통합 스트림 관리 스크립트 `manage_stream.sh`가 3채널 RTSP 수신, Qdrant 기동, 파이프라인 실행을 단일 명령으로 제어하는지 검증한다. 비정상 종료 후 자동 재시작 로직과 로그 로테이션 설정이 프로덕션 환경에 적합한지 점검한다.

**3-9. 에지 장비 모니터링 카드**
* Jetson의 CPU/GPU 사용률, VRAM 점유량, 코어 온도를 `jtop` Python API를 통해 주기적으로 수집하고 서버로 전송한다. 온도 임계값(예: 80°C 이상) 초과 시 경고 알림을 발생시키는 로직도 포함한다.

**3-10. E2E 전체 시스템 통합 테스트**
* 실 IP 카메라 → Jetson 에지 파이프라인 → FastAPI 서버 → PostgreSQL/Qdrant → 웹 대시보드로 이어지는 전체 경로를 PRD Definition of Done 체크리스트 기준으로 검증한다. 3채널 45 FPS 이상 유지, Re-ID Rank-1 ≥ 80%, 대시보드 500ms 이내 갱신, Docker 배포 가능, RTSP 자동 복구 동작을 순서대로 확인하고 결과를 기록한다.

- Jetson에서 s/m 이상 모델은 TensorRT 없이 FPS 목표 달성 어려움

### 4.2 2단계: Motion Tracking 대안

BoxMOT 라이브러리가 이미 도입돼 있어 **`create_tracker()` 인자 변경만으로** 대부분 교체 가능.

| 트래커 | Re-ID 내장 | 가림 복원 | 속도 | 특징 |
|---|:---:|:---:|:---:|---|
| **ByteTrack** (현재) | ✗ | 중 | 매우 빠름 | 저신뢰도 탐지도 활용, 단순·안정적 |
| **OC-SORT** | ✗ | 상 | 빠름 | 가림 구간 관측값 기반 보정, ByteTrack보다 재매칭 강함 |
| **BotSORT** | ✓ (선택) | 상 | 빠름 | ByteTrack + 카메라 모션 보정 + Re-ID 재매칭 |
| **StrongSORT** | ✓ | 상 | 중간 | DeepSORT 개선판, Re-ID 통합 강화 |
| **Deep OC-SORT** | ✓ | 매우 상 | 중간 | OC-SORT + Re-ID 결합, 현재 SOTA급 |
| DeepSORT | ✓ | 중 | 중간 | 고전적 방법, StrongSORT에 밀림 |
| SORT | ✗ | 하 | 매우 빠름 | 가장 단순, 가림에 취약 |

#### 4.2.1 트래커 선택에 따른 파이프라인 구조 변화

트래커 종류에 따라 Re-ID와의 통합 방식이 달라진다.

| 구조 | 해당 트래커 | 특징 |
|---|---|---|
| **탐지 → 트래킹 → Re-ID 분리** (현재) | ByteTrack, OC-SORT, SORT | Re-ID를 완전 분리 제어, VRAM 효율적 |
| **탐지 → Re-ID 내장 트래킹** | BotSORT, StrongSORT, Deep OC-SORT | 트래커 내부 Re-ID + OSNet Re-ID 이중 실행 → Jetson VRAM 추가 소비 주의 |

> Re-ID 내장 트래커 사용 시 트래커 내부 Re-ID 모델을 OSNet 동일 가중치로 통일해야 임베딩 분포 일관성 유지 가능.

#### 4.2.2 실용적 추천 변경 조합

| 목적 | 추천 변경 | 변경 비용 |
|---|---|:---:|
| 가림 대응 즉시 개선 | ByteTrack → **OC-SORT** | 설정값 변경만 |
| 재연결 후 ID 복원 강화 | ByteTrack → **BotSORT** (Re-ID 선택 사용) | 설정값 변경만 |
| 탐지율 개선 (밀집·실내) | YOLOv8n → **CrowdHuman 파인튜닝 YOLOv8n** | 가중치 파일 교체만 |
| 최신 경량 모델 테스트 | YOLOv8n → **YOLO11n** | 가중치 파일 교체만 |
| 최고 정확도 추적 (속도 감수) | ByteTrack → **Deep OC-SORT** | 설정값 변경 + VRAM 검증 |

### 4.3 YOLO 탐지 성능 측정 방법

#### 4.3.1 Re-ID 파이프라인에서 YOLO의 역할과 핵심 지표

YOLO는 파이프라인의 **입력 관문**이다. YOLO가 사람을 놓치면(FN) Re-ID 단계에 데이터 자체가 도달하지 않으므로, Re-ID 성능이 아무리 좋아도 의미가 없다. 반대로 YOLO가 사람이 아닌 것을 사람으로 탐지하면(FP) 가짜 Re-ID 벡터가 생성돼 매칭 오류를 유발한다.

| 지표 | 의미 | Re-ID 파이프라인 영향 |
|---|---|---|
| **Recall (탐지율)** | 실제 사람 중 몇 %를 탐지했는가 | 낮으면 Re-ID 입력 누락 직접 발생 |
| **Precision** | 탐지 결과 중 실제 사람 비율 | 낮으면 가짜 임베딩 벡터가 DB에 삽입됨 |
| **mAP@0.5** | IoU 0.5 기준 표준 종합 지표 | 모델 교체 시 비교 기준 |
| **FPS** | 초당 처리 프레임 수 | Jetson 45 FPS 목표 달성에 직접 영향 |

#### 4.3.2 방법 A — 현재 데이터로 간접 추정 (즉시 가능)

어노테이션 없이 기존 pkl 파일만으로 YOLO 탐지 품질을 진단한다.

**진단 항목:**

| 진단 신호 | 의미 |
|---|---|
| 단명 트랙 (`< 10프레임`) | YOLO가 순간적으로 잘못 탐지한 FP 후보 |
| `frag_pairs` 건수 | YOLO 누락으로 트랙이 끊긴 FN 의심 쌍 |
| 작은 bbox 면적 (`< 2000px²`) | 저화질·소형 탐지 — 신뢰도 낮음 |
| `track_quality.min_sim` 급락 | YOLO가 다른 사람을 같은 트랙에 끼워 넣은 의심 |

```python
import pickle, numpy as np

d = pickle.load(open('edge/notebooks/results/16300000.pkl', 'rb'))

# ── 단명 트랙 (FP 후보) ────────────────────────────────────────────────────────
short = {tid: recs for tid, recs in d['data_x025'].items() if len(recs) < 10}
print(f'단명 트랙(< 10프레임) 비율: {len(short)}/{len(d["data_x025"])} '
      f'({100*len(short)/len(d["data_x025"]):.1f}%)')

# ── 동일인 단절 쌍 (YOLO FN 의심) ────────────────────────────────────────────
print(f'frag_pairs (YOLO 누락 의심): {len(d["frag_pairs"])}쌍')

# ── bbox 면적 분포 ─────────────────────────────────────────────────────────────
areas = []
for recs in d['data_x025'].values():
    for r in recs:
        x1, y1, x2, y2 = r['bbox']
        areas.append((x2-x1) * (y2-y1))
areas = np.array(areas)
print(f'bbox 면적: mean={areas.mean():.0f}  p5={np.percentile(areas,5):.0f}  '
      f'min={areas.min():.0f}  (< 2000px²: {(areas<2000).mean()*100:.1f}%)')
```

**한계**: 실제 정답(ground truth)이 없으므로 문제 징후 파악 수준이며, 정밀한 수치는 아님.

#### 4.3.3 방법 B — 공개 데이터셋 벤치마크

어노테이션 없이 COCO 또는 CrowdHuman 데이터셋으로 모델 간 수치를 비교한다.

```python
from ultralytics import YOLO

model = YOLO('yolov8n.pt')

# COCO val2017에서 사람 클래스(class=0)만 평가
metrics = model.val(data='coco.yaml', classes=[0])
print(f"mAP@0.5   : {metrics.box.map50:.3f}")
print(f"Precision : {metrics.box.p:.3f}")
print(f"Recall    : {metrics.box.r:.3f}")
```

**주요 모델 참고 수치** (COCO Person 기준, 공개 벤치마크):

| 모델 | mAP@0.5 | Recall | 비고 |
|---|:---:|:---:|---|
| YOLOv8n (현재) | ~0.52 | ~0.72 | 범용 경량 모델 |
| YOLOv8s | ~0.60 | ~0.78 | 정확도/속도 균형 |
| YOLO11n | ~0.55 | ~0.74 | 최신 경량 모델 |
| CrowdHuman 파인튜닝 YOLOv8n | ~0.68 | ~0.85 | 밀집 실내 특화 |

> ⚠️ COCO는 실외·다양한 스케일 중심. 실내 고정 카메라 환경과 도메인 시프트가 있어 실제 성능은 다를 수 있음.

#### 4.3.4 방법 C — 실제 영상 직접 어노테이션

보유한 영상에서 50~100 프레임을 직접 라벨링해 실환경 기준 mAP를 측정한다.

**도구**: [CVAT](https://cvat.ai) (무료 웹 기반) 또는 `labelImg`

**흐름**:
```
avi 영상 → CVAT에서 50~100 프레임 선택 → 사람 BBox 수동 라벨링
    → YOLO 형식 어노테이션 내보내기 → ultralytics val() 로 평가
```

```python
from ultralytics import YOLO

model = YOLO('yolov8n.pt')

# CVAT에서 내보낸 YOLO 형식 데이터셋으로 직접 평가
# my_indoor.yaml: 실내 영상 어노테이션 데이터셋 경로 정의 파일
metrics = model.val(data='my_indoor.yaml')
print(f"실환경 mAP@0.5 : {metrics.box.map50:.3f}")
print(f"실환경 Recall  : {metrics.box.r:.3f}")
```

**기대 작업량**: 영상 1개 기준 50프레임 라벨링 → 약 1~2시간.

**활용**: 실측 Recall이 낮으면 CrowdHuman 파인튜닝 YOLOv8n으로 교체를 검토 (Section 4.1 참조).

#### 4.3.5 방법별 추천 시점

| 방법 | 추천 시점 | 소요 시간 | 결과 정밀도 |
|---|---|:---:|:---:|
| **A. 간접 추정** | 당장 문제 파악이 필요할 때 | 즉시 | 낮음 (징후) |
| **B. 공개 벤치마크** | 모델 교체 전 후보 비교 시 | 1~2시간 | 중간 (참고치) |
| **C. 직접 어노테이션** | Phase 2 진입 전 실환경 기준 확정 시 | 반나절 | 높음 (실측치) |

> **현재 권장**: 방법 A로 frag_pairs·단명 트랙 수를 확인해 YOLO FN이 Re-ID 성능 저하의 주 원인인지 먼저 파악한다. FN 비율이 높다면 방법 B·C로 모델 교체 효과를 검증한다.

### 4.4 추적기(ByteTrack) 품질 진단 방법론

#### 4.4.1 현재 노트북에서 측정하는 지표

시각 확인만 하는 것이 아니며 정량 지표 3가지가 이미 존재함.

| 진단 항목 | 방식 | 출력 지표 |
|---|---|---|
| 트랙별 썸네일 그리드 | 시각적 | 육안 확인 |
| 연속 프레임 임베딩 유사도 | **정량** | `mean_sim`, `min_sim`, `std`, `switch_rate` |
| 트랙 간 동일 인물 탐색 (fragmentation) | **정량** | fragmentation 쌍 수, 쌍별 유사도 |

실측 예시 (`14300002.avi`):
```
Track 2  프레임=1574  인접평균=0.986  switch율=0.0%
Track 3  프레임=1307  인접평균=0.982  switch율=0.1%  ← ID switch 1건 의심
fragmentation: Track 2 <-> Track 5  유사도=0.898  (동일 인물)
fragmentation: Track 3 <-> Track 6  유사도=0.766  (동일 인물)
```

#### 4.4.2 현재 방식의 한계

현재 지표는 모두 **임베딩 유사도 기반 proxy 지표**. Re-ID 모델이 틀리면 추적기 평가도 함께 오염됨.

MOT 분야 표준 지표는 별개로 존재:

| 표준 지표 | 의미 | 필요 조건 |
|---|---|---|
| **MOTA** | FP + FN + ID Switch 통합 정확도 | Ground truth 라벨 |
| **IDF1** | ID 연속성 기반 F1 점수 | Ground truth 라벨 |
| **HOTA** (최신 표준) | 탐지 정확도 + 연관 정확도 분리 측정 | Ground truth 라벨 |
| **IDsw** | ID 교체 횟수 절댓값 | Ground truth 라벨 |

표준 지표 측정을 위해서는 영상 구간의 BBox + 인물 ID를 수동 라벨링한 뒤 `py-motmetrics` 또는 `TrackEval` 라이브러리 사용 필요.

#### 4.4.3 방식별 비교 및 권장 시점

| 방식 | 비용 | 신뢰도 | 권장 시점 |
|---|---|:---:|---|
| **현재 방식** (임베딩 proxy) | 낮음 | 중간 | 개발 중 빠른 반복 진단 |
| **짧은 클립 수동 라벨링** (절충안) | 중간 | 높음 | 실기기 배포 전 1회 검증 |
| **Ground truth 전체 라벨링** (MOTA/IDF1) | 높음 | 높음 | 최종 성능 보고서·논문 |

> 실기기(Jetson) 배포 전 **50~100명 규모의 짧은 클립 1개를 수동 라벨링**해서 MOTA/IDF1을 한 번 측정해두면, Re-ID 모델 개선 효과를 추적기 성능과 분리해서 명확히 볼 수 있음.

## 5. OSNet 도메인 파인튜닝 실행 가이드

> 수동 프레임 캡처 불필요. 기존 파이프라인 도구로 80~90% 자동화 가능.

### 5.1 전체 흐름

```
동영상 파일 (보유 중)
    ↓ 자동
YOLO + ByteTrack → Track ID별 크롭 이미지 추출
    ↓ 자동 + 소량 수동 검증
영상 간 동일인 연결 (Person ID 확정)
    ↓ 자동
Market-1501 형식 디렉터리 구성
    ↓ 자동
Torchreid 파인튜닝 실행
```

### 5.2 1단계: 크롭 이미지 자동 추출

`results/*.pkl` 파일에 이미 Track ID별 크롭 썸네일(`thumbnail` 필드)이 저장돼 있음. 아래 스크립트로 즉시 파일로 추출 가능.

```python
import pickle, cv2, pathlib

for pkl_file in pathlib.Path("results").glob("*.pkl"):
    data = pickle.load(open(pkl_file, "rb"))
    video_name = pkl_file.stem

    for track_id, records in data["data_x025"].items():
        out_dir = pathlib.Path(f"reid_dataset/raw/{video_name}/track_{track_id:04d}")
        out_dir.mkdir(parents=True, exist_ok=True)

        for rec in records:
            cv2.imwrite(
                str(out_dir / f"f{rec['frame']:06d}.jpg"),
                rec["thumbnail"]   # 이미 크롭된 인물 이미지
            )
```

### 5.3 2단계: Person ID 매핑 (영상 간 동일인 연결)

Track ID는 영상 내에서만 유효하므로 영상 간 동일인을 연결해야 함.

**자동 처리**: 노트북 섹션 10의 `track_pair_sim()` 함수로 영상 간 트랙 유사도를 계산해 자동 클러스터링
```
video_A / track_2  ↔  video_B / track_5  (유사도 0.898)  → 동일 Person ID 부여
```

**수동 검증 (최소화)**: 자동 매칭 결과를 썸네일 그리드로 확인 → 오류만 수정.
인물 50명 기준 **1~2시간** 내 완료 가능.

### 5.4 3단계: Market-1501 형식으로 정리

Torchreid가 요구하는 디렉터리 구조.

```
reid_dataset/
  bounding_box_train/
    0001_c1_f000001.jpg    # 인물ID_카메라ID_프레임번호
    0001_c1_f000050.jpg
    0001_c2_f000120.jpg    ← 같은 사람, 다른 카메라/시점
    0002_c1_f000001.jpg
    ...
  query/
  bounding_box_test/
```

2단계에서 확정된 Person ID를 파일명 앞에 붙이는 rename 스크립트로 자동화 가능.

### 5.5 4단계: Torchreid 파인튜닝 실행

```python
import torchreid

# 데이터 로더 (Re-ID 전용 증강 포함)
datamanager = torchreid.data.ImageDataManager(
    root="reid_dataset",
    sources="market1501",
    targets="market1501",
    height=256, width=128,
    batch_size=32,
    transforms=["random_flip", "random_crop", "random_erasing", "color_jitter"]
)

# 사전학습 가중치에서 시작 (MSMT17 기반)
model = torchreid.models.build_model(
    name="osnet_x0_25",
    num_classes=datamanager.num_train_pids,
    pretrained=True
)

# ID Loss + Triplet Loss 조합 권장
engine = torchreid.engine.ImageSoftmaxEngine(
    datamanager, model,
    lr=0.0003,          # 파인튜닝은 낮은 lr 사용
    weight_decay=5e-4,
)

engine.run(
    max_epoch=60,
    save_dir="finetuned_osnet",
    eval_freq=10,
)
```

### 5.6 데이터 요건 및 기대 효과

| 수집 인물 수 | 인물당 이미지 수 | 조건 | 예상 Rank-1 향상 |
|:---:|:---:|---|---|
| 10~20명 | 6장 이상 | 단일 카메라 | +5~10%p |
| 30~50명 | 10장 이상 | 다각도 포함 | +10~15%p |
| **50명 이상** | **카메라 2개 이상 뷰** | 다양한 조명·의상 | **80% 목표 달성 가능** |

> 현재 보유한 동영상 4개(pkl 파일 기준)의 추출 가능 인물·크롭 수를 먼저 확인하는 것이 시작점.
> 인물 수가 부족하면 실제 카메라 설치 환경에서 추가 촬영 필요 (Action Item 2-3).

### 5.7 주의사항

- **모델 가중치 동기화**: 파인튜닝 완료 후 에지(edge)와 서버(server) 양측의 OSNet 가중치를 동일 파일로 교체해야 임베딩 분포가 일치함 (Action Item Common - OSNet 가중치 일치, Done 참조)
- **ONNX 재변환 필요**: 파인튜닝 후 `.pt` → `.onnx` 재변환 필요. `ReIDExtractor`의 Auto-Export 로직이 자동 처리하지만, 기존 캐시된 `.onnx` 파일을 삭제한 후 재실행해야 함
- **임계값 재조정**: 파인튜닝 후 임베딩 분포가 달라지므로 노트북으로 최적 임계값을 재계산해야 함 (Action Item 1-1 재수행)

### 9.4 80% 달성을 위한 현실적 경로

1. **도메인 파인튜닝** (가장 효과적): 실제 설치 환경 영상으로 OSNet 추가 학습
2. **Temporal Pooling 구현** (§2.3 3순위 개선안): 여러 프레임 벡터 평균으로 단일 프레임 노이즈 상쇄
3. **osnet_x1_0 + 파인튜닝 병행**: 단독 교체는 효과 없었으나(d' 2.13→2.05), 파인튜닝과 병행하면 의미 있음
4. **TransReID 등 ViT 모델 도입**: 정확도는 높지만 Jetson에서 속도 제약 있음

실용적으로는 **①파인튜닝 + ②Temporal Pooling** 조합이 하드웨어 제약 내에서 80%에 가장 빠르게 도달하는 경로.

### 9.5 SOTA 모델 FN율 비교 및 Phase별 목표

Re-ID 학술 벤치마크는 FN/FP를 직접 보고하지 않고 **Rank-1 / mAP**로 평가한다. FN은 임계값에 따라 달라지는 운영 지표이므로 Rank-1에서 간접 추론이 필요하다.

| 모델 | Rank-1 (Market-1501) | 랭킹 기준 miss rate | 실환경 FN 추정 (FP≈0% 기준) |
|---|:---:|:---:|:---:|
| CLIP-ReID / TransReID | ~96% | ~4% | ~15~25% |
| OSNet-x1.0 | ~95% | ~5% | ~20~30% |
| **OSNet-x0.25 (현재)** | ~89% | ~11% | ~30~45% |

> 랭킹 기준 miss rate는 임계값 없는 순수 랭킹 오류율. 실환경에서 FP를 억제하는 임계값을 적용하면 FN은 급격히 올라간다. SOTA 모델도 실환경 FN 10% 이하는 쉽지 않다.

#### 20% 목표 적정성 평가

| 관점 | 평가 |

| 현재 실측 (임계값 0.85) | FN 39.4% → Phase 1 목표 대비 2배 초과 |

| PRD Use Case 요구 수준 | SS-01 실종자 추적: 낮은 FN 필수 / SR-01 VIP 인식: 20% 허용 가능 |

20%는 **Phase 1 달성 가능한 현실적 출발점**이지만 최종 목표로는 느슨하다. 파인튜닝 후 SOTA 실환경 수준(~10%)에 근접하는 것이 실질적인 목표치다.

### 9.6 mAP 목표 설정 및 평가 방법

#### SOTA mAP 비교 (Market-1501 기준)

Rank-1과 mAP는 Re-ID 벤치마크의 표준 지표 쌍이다. mAP는 Rank-1보다 항상 낮으며 격차가 크다.

| 모델 | Rank-1 | mAP | 갭 |
|---|:---:|:---:|:---:|
| OSNet-x0.25 (현재) | ~84% | ~60% | -24%p |
| OSNet-x1.0 | ~94% | ~73% | -21%p |
| TransReID | ~95% | ~83% | -12%p |
| CLIP-ReID / SOTA | ~96% | ~89% | -7%p |

> 실환경 도메인 시프트 후에는 갭이 더 벌어진다. OSNet-x0.25 실환경 mAP는 40~50% 수준으로 추정.

#### Rank-1 vs mAP — 무엇이 다른가

| 지표 | 의미 | 중요한 Use Case |
|---|---|---|
| **Rank-1** | 1위 매칭이 맞는 확률 | SR-01 VIP 실시간 인식, 알림 |
| **mAP** | 해당 인물의 모든 출현을 빠짐없이 찾는 정도 | SS-01 실종자 전수 조사, 동선 재구성 |

#### Phase별 mAP 목표

| Phase | mAP 목표 | 현재 | 달성 방법 |
|:---:|:---:|:---:|---|
| **Phase 1** | **≥ 45%** | 미측정 | 노트북 mAP 평가 구현 후 기준값 확인 |
| **Phase 2** | **≥ 60%** | — | 도메인 파인튜닝 후 |
| **Phase 3** | **≥ 55%** | — | RTSP 실환경 열화 감안 완화 |

> Phase 1 목표 45%는 범용 가중치 수준 추정치. 실측 후 재조정 가능.

#### mAP 평가 구현 방법 (노트북 추가 코드)

```python
from sklearn.metrics import average_precision_score
import numpy as np

def compute_map(query_embeddings, query_ids, gallery_embeddings, gallery_ids):
    """gallery/query 분리 기반 mAP 계산"""
    aps = []
    for q_emb, q_id in zip(query_embeddings, query_ids):
        sims = gallery_embeddings @ q_emb / (
            np.linalg.norm(gallery_embeddings, axis=1) * np.linalg.norm(q_emb) + 1e-8
        )
        sorted_idx = np.argsort(-sims)
        relevance = (gallery_ids[sorted_idx] == q_id).astype(int)
        if relevance.sum() > 0:
            aps.append(average_precision_score(relevance, sims[sorted_idx]))
    return np.mean(aps)

# 실용적 설정: pkl 트랙 임베딩에서 절반 query / 절반 gallery로 분리 후 계산
```

## 10. RTSP 스트림 환경에서의 추가 성능 열화 및 대응 방법

> 노트북 분석은 로컬 파일 기반 최적 조건에서 측정됨. 실제 RTSP 스트림 환경에서는 추가 열화 요인이 존재.

### 10.1 열화 요인 및 예상 영향

> **참고**: 현재 분석에 사용 중인 동영상 파일(`.avi`)은 IP 카메라 → 네트워크를 통해 수신된 H.264/H.265 압축 파일이다. 따라서 압축 아티팩트는 **현재 기준값(61.5%)에 이미 포함**되어 있으며, 아래 표는 파일 기반 순차 처리 대비 **실시간 RTSP 파이프라인에서 추가로 발생하는 열화 요인**만 기술한다.

| 요인 | 원인 | 예상 Rank-1 추가 하락 |
|---|---|:---:|
| 프레임 드롭에 의한 샘플 감소 | 최신 프레임 보존 Drop 전략으로 Best-shot 후보 유실 | -2~5%p |
| 스트림 재연결 트래커 리셋 | RTSP 끊김 시 ByteTrack Track ID 초기화 | ID Switching 증가 |
| 네트워크 지터 | 프레임 도착 간격 불규칙 → 칼만 필터 예측 오차 | -1~3%p |
| **합산** | | **-3~8%p 추가 하락** |

파일 기반 최선(71%) 기준으로 실 스트림에서는 **63~68% 수준**으로 떨어질 가능성 있음.

### 10.2 요인별 극복 방법

#### A. 영상 품질 개선 대응

> 현재 기준값(61.5%)에는 원본 촬영 당시 네트워크 압축 아티팩트가 이미 반영돼 있다. 아래 방법들은 압축이 심한 저품질 프레임을 배제하거나, Phase 3 실 카메라 설치 시 더 높은 화질로 시작점을 높이기 위해 적용한다.

| 방법 | 설명 | 구현 비용 |
|---|---|:---:|
| **화질 게이트 (Quality Gate)** | 라플라시안 분산(선명도 점수)으로 저품질 프레임 Re-ID 스킵. 압축 여부와 무관하게 모션 블러·블로킹 심한 프레임 배제 | 코드 20줄 수준 |
| **I-프레임 우선 Re-ID 추출** | RTSP 스트림에서 압축 손실이 적은 I-프레임에서만 Re-ID 추출, P/B 프레임은 추적에만 사용 | 중간 |
| **전처리 강화** | 기존 CLAHE + Unsharp Masking에 디블로킹 필터 추가 (`cv2.fastNlMeansDenoising`) | 낮음 |
| **카메라 비트레이트 상향** (Phase 3) | 실 IP 카메라 설정에서 최소 2Mbps 이상 확보. 원본 촬영보다 높은 비트레이트 설정 시 현재 기준값보다 화질 향상 가능 | 설정 변경만 |

#### B. 프레임 드롭 전략 개선

| 방법 | 설명 | 구현 비용 |
|---|---|:---:|
| **Re-ID 전용 큐 분리** | 실시간 표시용 큐(크기 1~2)와 Re-ID 추출용 큐(크기 5~10) 분리 — 표시는 드롭해도 Re-ID는 버퍼 유지 | 중간 |
| **탐지 신뢰도 기반 선택적 드롭** | YOLO confidence 높은 프레임은 드롭 제외 | 중간 |
| **Re-ID 추출 주기 분리** | Re-ID를 N프레임마다 실행, 나머지는 추적만 수행 | 낮음 |

#### C. 스트림 재연결 트래커 복원

| 방법 | 설명 | 구현 비용 |
|---|---|:---:|
| **`max_missing_frames` 튜닝** | 재연결 예상 시간에 맞게 값 상향 → 짧은 끊김에서 Track ID 유지 (기존 구조 활용) | 설정값 변경만 |
| **재연결 후 로컬 Re-ID 매칭** | 재연결 직후 탐지된 인물을 로컬 Qdrant 최근 벡터와 비교 → 기존 ID 재부여 | 높음 |
| **트래커 상태 스냅샷 저장** | 끊김 직전 활성 Track의 마지막 BBox + 벡터를 SQLite에 보존 후 복원 | 높음 |

#### D. 네트워크 지터 대응

| 방법 | 설명 | 구현 비용 |
|---|---|:---:|
| **지터 버퍼 (Jitter Buffer)** | GStreamer `rtpjitterbuffer` 적용 — 일정 지연 감수하고 프레임 간격 균일화 | 중간 |
| **타임스탬프 기반 처리** | 프레임 도착 시각 대신 카메라 하드웨어 타임스탬프 기준으로 트래커 업데이트 | 중간 |

### 10.3 대응 우선순위

| 순위 | 방법 | 예상 회복 효과 | 구현 비용 |
|:---:|---|---|:---:|
| 1 | **`max_missing_frames` 튜닝** | 짧은 재연결 ID Switching 방지 | 설정값 변경만 |
| 2 | **화질 게이트 (라플라시안 필터)** | 저품질 프레임 Re-ID 스킵 → FN 감소 | 낮음 |
| 3 | **Re-ID 전용 큐 분리** | Best-shot 품질 보장 → Rank-1 회복 | 중간 |
| 4 | **I-프레임 우선 Re-ID 추출** | 실시간 RTSP 압축 아티팩트 최소화 | 중간 |
| 5 | **재연결 후 로컬 Re-ID 매칭** | 재연결 시 ID 연속성 유지 | 높음 |
| 6 | **카메라 비트레이트 상향** (Phase 3) | 실 카메라 설정 시 현재 기준값보다 높은 화질 확보 | 설정 변경만 |

> 1~2순위는 설정값·코드 최소 변경으로 즉시 적용 가능. 3~5순위는 파이프라인 수준 개선 필요. 6순위는 Phase 3 실 카메라 설치 시 적용 (현재 파일 기반 비교에는 해당 없음).

## 11. RTSP 실시간 파이프라인 성능 측정 방법

> Action Item 2-1 수행 시 활용. 파일 순차 처리(노트북) 대비 실시간 RTSP 파이프라인에서 추가로 발생하는 열화를 정량화하는 방법.

### 11.1 측정 목적 재정의

> ⚠️ **이중 압축 주의**: 현재 `.avi` 파일은 이미 네트워크를 통해 수신된 H.264/H.265 압축 파일이다. 이 파일을 FFmpeg로 재인코딩해 RTSP 송출하면 **H.264 → H.264 이중 압축**이 발생해 원본보다 훨씬 열악한 조건이 만들어진다. 이 방식으로 측정한 결과는 실제 RTSP 환경보다 과도하게 비관적이므로 해석에 주의해야 한다.

| 측정 대상 | 올바른 방법 | 주의사항 |
|---|---|---|
| **프레임 드롭 / 지터 효과** | 실제 파이프라인 실행 (실시간 처리) vs 파일 순차 처리 비교 | `-vcodec copy`로 재인코딩 없이 송출 |
| **재연결 트래커 리셋 효과** | `tc netem` 네트워크 차단 → 복구 후 ID 연속성 측정 | 압축 변경 없이 네트워크 조건만 변경 |
| **추가 압축 열화 측정** | 원본 촬영 비트레이트보다 **낮은** 비트레이트로만 유효 | 동일/이상 비트레이트 재인코딩은 이중 압축으로 무의미 |

**핵심**: RTSP 테스트의 목적은 압축 열화 측정이 아니라, **실시간 처리 조건 (프레임 드롭·지터·재연결)** 이 Re-ID 성능에 미치는 영향을 측정하는 것이다.

### 11.2 올바른 RTSP 성능 측정 흐름

파일을 저장 후 재분석하는 방식이 아니라, 실시간 파이프라인을 직접 실행해 측정한다.

```
[파일 기반 측정 - 기준값]
.avi 파일 → OpenCV VideoCapture → YOLO → ByteTrack → Re-ID → pkl 저장
→ reid_performance.ipynb 분석 → Rank-1 61.5%

[RTSP 실시간 측정]
.avi 파일 → Mediamtx RTSP 송출 (-vcodec copy) → 실시간 파이프라인 실행
(프레임 드롭 전략 작동, 지터 발생, 재연결 시 리셋 발생)
→ 실시간 Re-ID 결과 pkl 저장 → 동일 노트북으로 분석 → Rank-1 비교
```

### 11.3 1단계: Mediamtx RTSP 에뮬레이터 송출

```bash
# 원본 파일을 RTSP로 실시간 송출 — 재인코딩 없이 원본 품질 그대로 전달
ffmpeg -re -stream_loop -1 -i data/14300002.avi \
  -vcodec copy \
  -f rtsp rtsp://localhost:8554/cam1
```

> `-vcodec copy` 옵션으로 재인코딩을 건너뛰어 이중 압축 문제를 방지한다.

### 11.4 2단계: (선택) 네트워크 열화 조건 주입

프레임 드롭과 지터 효과만 측정하려면 압축 변경 없이 네트워크 조건만 변경한다.

```bash
# 지연 50ms + 지터 20ms + 패킷 손실 2% 주입 (압축 변경 없음)
sudo tc qdisc add dev lo root netem delay 50ms 20ms loss 2%

# 테스트 후 복구
sudo tc qdisc del dev lo root
```

### 11.5 3단계: 실시간 파이프라인 실행 및 결과 저장

파일을 저장 후 재분석하는 대신, **실시간 파이프라인을 직접 실행**하고 결과를 pkl로 저장한다.

```python
# 실시간 RTSP 처리 — 결과를 pkl로 저장해 노트북과 동일 방식으로 비교
from edge.pipeline import PipelineRunner

runner = PipelineRunner(
    source="rtsp://localhost:8554/cam1",
    output_pkl="results/14300002_rtsp_realtime.pkl"
)
runner.run()

# reid_performance.ipynb에서
# PKL_PATH = "results/14300002.pkl"              → Rank-1 61.5% (파일 기반 기준값)
# PKL_PATH = "results/14300002_rtsp_realtime.pkl" → RTSP 실시간 결과
```

### 11.6 추가 압축 열화 측정이 필요한 경우

원본 파일 촬영 당시보다 낮은 비트레이트에서의 성능 열화를 확인할 때만 의미가 있다.

```bash
# 원본보다 낮은 비트레이트로 재인코딩해 송출 (이 조건만 비교 유효)
ffmpeg -re -stream_loop -1 -i data/14300002.avi \
  -vcodec libx264 \
  -b:v 512k -maxrate 512k -bufsize 1M \
  -f rtsp rtsp://localhost:8554/cam1_low
```

| 테스트 시나리오 | 유효성 | 이유 |
|---|:---:|---|
| 원본 비트레이트 이상으로 재인코딩 | ✗ | 이중 압축으로 원본보다 나쁜 조건 → 해석 불가 |
| `-vcodec copy` 원본 그대로 RTSP 송출 | ✓ | 이중 압축 없음 — 실시간 처리 효과만 측정 |
| 원본보다 낮은 비트레이트로 재인코딩 | ✓ | 저비트레이트 추가 영향 측정 가능 |
| Phase 3 실 IP 카메라에서 비트레이트 직접 조정 | ✓ | 가장 이상적 — 이중 압축 없음 |

### 11.7 기대 분석 결과

| 조건 | 예상 Rank-1 | 비교 목적 |
|---|:---:|---|
| 파일 기반 처리 (현재 실측) | **61.5%** | 기준값 |
| RTSP 실시간 (`-vcodec copy`, 지터 없음) | ~60~65% | 실시간 처리 (프레임 드롭) 영향 |
| RTSP + `tc netem` 패킷 손실 1~2% | ~58~63% | 네트워크 불안정 추가 영향 |
| RTSP 원본보다 낮은 비트레이트 (512kbps) | ~48~58% | 저비트레이트 임계점 탐색 |
| Phase 3 실 카메라 고비트레이트 (≥4Mbps) | 기준값 이상 가능 | 카메라 화질 향상 효과 확인 |

→ **파일 기반 처리 vs RTSP 실시간 처리** 차이가 실제 프레임 드롭·지터 영향량.
→ Phase 3 실 카메라에서는 비트레이트를 원본 파일보다 높게 설정해 기준값 이상의 화질 확보 가능.

## 12. 인텔 GPU (XPU) 가속 설정 가이드

로컬 검증 및 분석 속도 가속을 위해 인텔 GPU(XPU)를 사용하여 PyTorch 연산을 실행할 때 필요한 설정 방법입니다.

### 12.1 PyTorch XPU 패키지 설치
PyTorch 2.4+ 이상부터는 공식 upstream 통합 버전으로 인텔 GPU(XPU)가 기본 빌드되어 있으므로, 레거시 IPEX 라이브러리 없이 공식 XPU 휠(wheel)만 설치하면 됩니다.
```bash
# 기존 버전 및 IPEX 제거
pip uninstall -y torch torchvision torchaudio intel-extension-for-pytorch

# 공식 PyTorch XPU 빌드 설치
pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/xpu
```

### 12.2 Ubuntu 24.04 (Noble) 그래픽 드라이버 및 Level-Zero 런타임 설치
인텔 GPU 하드웨어를 파이썬 SYCL 환경과 바인딩하기 위해 Level-Zero 그래픽 패키지를 OS 수준에 설치해야 합니다.
```bash
# 공식 인텔 그래픽스 PPA 등록 및 필수 패키지 설치
sudo apt update
sudo apt install -y software-properties-common
sudo add-apt-repository -y ppa:kobuk-team/intel-graphics
sudo apt update
sudo apt install -y libze-intel-gpu1 libze1 intel-opencl-icd libze-dev
```

### 12.3 일반 사용자 계정 GPU 장치 접근 권한 설정
기본적으로 리눅스 커널의 GPU 디바이스 파일(`/dev/dri/renderD128` 등)은 일반 사용자의 접근이 제한되어 있습니다.
```bash
# 사용자 계정을 render, video 그룹에 추가
sudo usermod -aG render,video $USER

# 현재 터미널 세션에 변경 사항 즉시 반영 (또는 터미널을 새로 열기)
newgrp render
newgrp video
```

## 15. YOLO · Tracker · Re-ID 단계별 오차 체계

### 15.1 오차 누적 구조

3단계 파이프라인에서 오차는 누적되며, **업스트림 오차는 다운스트림에서 수정 불가**하다.

```
YOLO 탐지 → ByteTrack 추적 → Re-ID 매칭
   ↓              ↓              ↓
  FN/FP       ID Switch       FN/FP
   ↓              ↓              ↓
          최종 Re-ID Rank-1
```

YOLO가 사람을 놓치면(FN) Re-ID는 해당 인물을 볼 기회 자체가 없다. 따라서 개선 우선순위를 결정하려면 오차를 단계별로 분리해서 측정해야 한다.

---

### 15.2 단계별 오차 분류

| 단계 | 오차 유형 | 다운스트림 영향 | 측정 지표 |
|---|---|---|---|
| **YOLO** | FN (사람 미검출) | Re-ID 입력 자체 소실 → 재인식 원천 불가 | Recall |
| **YOLO** | FP (비사람 검출) | 가짜 임베딩 DB 삽입 → FP 매칭 유발 | Precision |
| **YOLO** | BBox 오차 (위치 부정확) | 크롭 품질 저하 → 임베딩 품질 저하 | IoU |
| **ByteTrack** | Track 분열 (Fragmentation) | 동일인이 2개 트랙 → Re-ID가 다른 사람으로 분리 판단 | frag_pairs, IDF1 |
| **ByteTrack** | ID Switch | 트랙 오염 → 평균 임베딩 품질 저하 | IDsw, switch_rate |
| **Re-ID** | FN (재인식 실패) | 같은 사람을 새 사람으로 등록 | FN율, Rank-1 |
| **Re-ID** | FP (오인식) | 다른 사람을 같은 사람으로 매칭 | FP율 |

---

### 15.3 오차 귀인(Attribution) 방법론

오차가 어느 단계에서 오는지 알아야 어디를 고칠지 결정할 수 있다.

#### 방법 1 — 단독 측정 (Decoupled Evaluation)

각 단계를 **완벽한 입력**으로 단독 평가해 세 숫자의 갭으로 단계별 책임을 분리한다.

```
GT BBox 크롭 → Re-ID 단독 평가  →  "이상적 크롭 조건에서 Re-ID 최대 성능"
GT Track 임베딩 → Re-ID 평가   →  "트래커 오차 제거 시 Re-ID 성능"
전체 파이프라인 → 최종 Rank-1  →  "현재 실측값 (세 단계 오차 혼합)"
```

> **EYE-D 현재 노트북 수치(71%)는 GT Track 임베딩이 아닌 실제 ByteTrack 출력 pkl 기반**이므로, YOLO BBox 오차·Track 분열 오염이 포함된 값이다. 깨끗한 트랙만 필터링해 Re-ID 단독 성능을 재측정하면 상한을 추정할 수 있다.

#### 방법 2 — 오라클 실험 (Oracle Experiment)

한 단계만 완벽(oracle)으로 대체해 해당 단계의 기여도를 직접 측정한다.

```
Oracle YOLO + 실제 Tracker + 실제 Re-ID   → Tracker + Re-ID 오차만 반영
실제 YOLO  + Oracle Tracker + 실제 Re-ID  → YOLO + Re-ID 오차만 반영
실제 전체 파이프라인                        → 세 단계 오차 합산
```

각 비교의 Rank-1 차이가 해당 단계의 오차 기여분이다.

#### 방법 3 — 민감도 분석 (Sensitivity Analysis)

각 단계의 오차율을 조금씩 변화시켜 최종 Rank-1 변화를 관찰한다. 임계값 스윕 실험이 이 방법의 Re-ID 버전이다. YOLO confidence threshold나 tracker의 `max_missing_frames` 변화에 따른 최종 Rank-1 변화도 동일한 방식으로 측정할 수 있다.

---

### 15.4 오차 예산(Error Budget)

최종 목표 Rank-1 ≥ 80%를 달성하려면 각 단계에 허용 오차를 역산해 배분해야 한다.

```
최종 Rank-1 ≈ YOLO Recall × (1 - Track 분열률) × Re-ID Rank-1 (단독)
           ≈ (1 - 0.10)  × (1 - 0.05)         × 0.94
           ≈ 0.80
```

| 단계 | 허용 오차 목표 | 현재 추정 | 갭 | 측정 방법 |
|---|---|---|---|---|
| YOLO Recall | ≥ 90% | 미측정 | 미지 | 방법 A 간접 진단 또는 어노테이션 |
| Track 분열률 | ≤ 5% | frag_pairs로 간접 확인 | 미지 | MOTA/IDF1 (Phase 2) |
| Re-ID Rank-1 (단독) | ≥ 94% | 오염 포함 71% | 미지 | 깨끗한 트랙 필터링 후 재측정 |

> 오차 예산 수식은 단순화된 근사이며, 단계 간 오차가 독립적이지 않을 때 (예: YOLO FP가 tracker를 거쳐 Re-ID FP를 유발) 실제 결과와 다를 수 있다.

---

### 15.5 EYE-D 실행 순서

```
Step 1 (즉시 · 비용 낮음)
  → pkl 간접 진단: 단명 트랙 비율, frag_pairs 수, switch_rate 확인
  → "YOLO/Tracker 오차가 심각한가 아닌가" 1차 판단 (Action Item 1-12, 1-13)

Step 2 (Phase 1 · 비용 낮음)
  → 노트북에서 Re-ID 단독 성능 측정
  → switch_rate > 0.1 또는 mean_sim < 0.6 인 오염 트랙 제외 후 Rank-1 재계산
  → "현재 71%가 Re-ID 한계인가, 오염 때문인가" 판단

Step 3 (Phase 2 · 비용 중간)
  → 짧은 클립 수동 라벨링 → MOTA/IDF1 측정 → Tracker 오차 정확히 분리 (Action Item 2-6)
  → YOLO mAP 측정 → 탐지 오차 정확히 분리 (§4.3)

Step 4 (Phase 2 완료 후)
  → 실측 수치로 오차 예산 재계산 → 개선 우선순위 결정
  → Rank-1 80% 도달에 Re-ID 파인튜닝이 필요한지, YOLO 교체가 더 효과적인지 수치로 판단
```

---

### 15.6 핵심 원칙

1. **업스트림 오차를 먼저 진단하라** — YOLO Recall이 낮으면 Re-ID를 아무리 개선해도 상한이 막혀 있다.
2. **오라클 실험으로 책임을 분리하라** — 현재 71%가 Re-ID의 한계인지, YOLO·Tracker 오염인지 구분해야 올바른 개선 방향이 나온다.
3. **오차 예산을 역산해 설정하라** — 최종 목표 80%에서 각 단계 허용 오차를 배분하고, 달성 불가능한 단계를 먼저 개선한다.
4. **proxy 지표의 한계를 인식하라** — 현재 pkl 기반 switch_rate·frag_pairs는 Re-ID 모델 품질과 혼합 측정된다. Phase 2의 수동 라벨링(MOTA/IDF1)이 나오기 전까지는 방향 판단용으로만 사용한다.

## 16. 용어집 (Glossary)

> 이 문서에서 반복적으로 등장하는 핵심 용어를 정리한다.

---

### 16.1 파이프라인 구조 관련

---

#### 16.1.1 업스트림(Upstream) / 업스트림 오차(Upstream Error)

**파이프라인에서 더 앞 단계, 또는 그 단계에서 발생한 오차.**

```
YOLO → ByteTrack → Re-ID
 ↑업스트림          ↑다운스트림
```

EYE-D 파이프라인에서 YOLO는 ByteTrack과 Re-ID의 업스트림이다. 업스트림에서 발생한 오차(예: YOLO가 사람을 놓침)는 **다운스트림 단계로 전달되며, 다운스트림에서 소급해서 수정할 수 없다.** YOLO가 사람을 탐지하지 못하면 ByteTrack과 Re-ID는 그 사람의 존재 자체를 모른다.

**실제 예시**:
- YOLO가 프레임에서 사람을 놓침(FN) → ByteTrack은 해당 프레임에서 트랙 단절로 처리 → Re-ID는 해당 구간의 임베딩을 받지 못함 → 재인식 실패

---

#### 16.1.2 다운스트림(Downstream) / 다운스트림 오차(Downstream Error)

**파이프라인에서 더 뒷 단계, 또는 그 단계에서 발생한 오차.**

```
YOLO → ByteTrack → Re-ID
                    ↑다운스트림
```

EYE-D에서 Re-ID는 YOLO와 ByteTrack의 다운스트림이다. 다운스트림 오차(예: Re-ID 임계값이 너무 엄격해 재인식 실패)는 해당 단계 내에서 수정이 가능하다(임계값 조정, 모델 교체 등). 단, **업스트림에서 이미 데이터가 소실되거나 오염된 경우에는 다운스트림 개선의 효과가 제한**된다.

**실제 예시**:
- Re-ID 임계값 0.85가 너무 높아 같은 사람을 새 사람으로 판단 → 0.73으로 낮춰 해결 가능 (다운스트림 내부에서 수정 가능한 오차)

---

### 16.2 오차 유형 관련

---

#### 16.2.1 FN (False Negative, 거짓 음성)

**실제로 존재하는 것을 "없다"고 판단하는 오차.**

| 단계 | FN의 의미 |
|---|---|
| **YOLO** | 화면에 사람이 있는데 탐지하지 못함 |
| **Re-ID** | 같은 사람인데 "다른 사람"으로 판단해 재인식 실패 |

FN이 높으면 사람이 누락되므로, SS-01(실종자 추적) 같은 use case에서 특히 치명적이다.

---

#### 16.2.2 FP (False Positive, 거짓 양성)

**실제로 없는 것을 "있다"고 판단하는 오차.**

| 단계 | FP의 의미 |
|---|---|
| **YOLO** | 사람이 아닌 것(기둥, 가방 등)을 사람으로 탐지 |
| **Re-ID** | 다른 사람인데 "같은 사람"으로 매칭해 오인식 |

FP가 높으면 가짜 임베딩이 DB에 쌓이거나, 엉뚱한 사람이 같은 사람으로 묶인다.

---

#### 16.2.3 ID Switch (ID 교체)

**ByteTrack이 동일인에게 부여했던 Track ID를 중간에 바꾸는 현상.**

예: A라는 사람이 Track 3으로 추적되다가 잠시 가려진 후 재등장했을 때 Track 7로 새로 부여됨. Re-ID 입장에서는 Track 3과 Track 7이 같은 사람인지 알 수 없어 재인식 오류로 이어진다.

`track_quality.n_switches`와 `switch_rate`로 간접 진단하며, 정확한 측정은 수동 라벨링 + `py-motmetrics`가 필요하다.

---

#### 16.2.4 Track 분열 (Track Fragmentation)

**동일인이 하나의 연속적인 트랙으로 유지되지 못하고 여러 개의 별개 트랙으로 쪼개지는 현상.**

주요 원인: YOLO가 특정 프레임에서 사람을 놓쳐(FN) 트랙이 끊기면, ByteTrack은 재등장 시 새로운 Track ID를 부여한다.

`frag_pairs` 항목에 유사도 기반으로 동일인으로 추정되는 트랙 쌍이 기록된다. Track 분열이 많으면 Re-ID가 같은 사람을 여러 명으로 분리 등록하는 오류로 이어진다.

---

### 16.3 측정 지표 관련

---

#### 16.3.1 Rank-1 정확도

**Re-ID 평가에서, 쿼리 인물과 가장 유사한 임베딩 1개가 실제로 같은 사람일 확률.**

100개의 쿼리 중 70개가 1위 매칭에서 정답이면 Rank-1 = 70%. 빠른 정확도 확인에 적합하지만 "모든 출현을 얼마나 빠짐없이 찾는가"는 측정하지 못한다.

---

#### 16.3.2 mAP (mean Average Precision) — Re-ID 맥락

**쿼리 인물의 모든 gallery 출현을 얼마나 빠짐없이, 그리고 높은 순위로 찾는가를 평균낸 지표.**

Rank-1은 "1등만 맞으면 되는 시험", mAP는 "그 사람의 모든 등장을 순서대로 얼마나 잘 찾는가"이다. 실종자 전수 조사(SS-01)처럼 한 명의 모든 이동 기록을 복원해야 하는 use case에서 Rank-1보다 더 중요한 지표다.

**계산 방법 (Re-ID 표준)**

1. 트랙 임베딩을 **query**(절반)와 **gallery**(절반)로 분리한다.
2. 각 query 임베딩에 대해 gallery 전체와 코사인 유사도를 계산하고 내림차순 정렬한다.
3. 정렬 결과에서 "해당 인물"이 나올 때마다 Precision을 누적해 **AP**(Average Precision)를 계산한다.
4. 모든 query의 AP를 평균낸 값이 **mAP**이다.

```
AP = (P@k₁ + P@k₂ + ... ) / 해당 인물의 gallery 등장 수
mAP = mean(AP_query1, AP_query2, ...)
```

**Re-ID mAP vs YOLO mAP@0.5**

| 항목 | Re-ID mAP | YOLO mAP@0.5 |
|---|---|---|
| 입력 | 임베딩 코사인 유사도 순위 | IoU 0.5 기준 bbox 탐지 |
| 분모 | gallery 내 동일인 출현 수 | GT bbox 수 |
| 용도 | 인물 재인식 전수 검색 정확도 | 탐지 모델 성능 비교 |

두 지표 모두 "mAP"로 표기되지만 **완전히 다른 맥락**이므로 혼동 주의.

**EYE-D Phase별 목표**

| Phase | mAP 목표 | 비고 |
|:---:|:---:|---|
| Phase 1 | ≥ 45% | 범용 가중치 추정치, 실측 후 재조정 가능 |
| Phase 2 | ≥ 60% | 도메인 파인튜닝 후 |
| Phase 3 | ≥ 55% | RTSP 실환경 열화 감안 완화 |

> 상세 내용: §9.6 참조.

---

#### 16.3.3 Proxy 지표 (Proxy Metric)

**직접 측정이 어려운 대상을 간접적으로 추정하기 위해 사용하는 대리 지표.**

EYE-D에서 수동 라벨링 없이 pkl 파일의 `switch_rate`, `mean_sim`, `frag_pairs`로 ByteTrack 품질을 진단하는 것이 proxy 지표 활용이다. 측정 비용이 낮은 대신, Re-ID 모델 품질과 혼합 측정되어 순수한 트래커 성능을 분리하지 못하는 한계가 있다.

---

#### 16.3.4 MOTA (Multi-Object Tracking Accuracy)

**추적기 성능의 표준 종합 지표. FP·FN·ID Switch를 하나의 수치로 통합.**

```
MOTA = 1 - (FP + FN + IDsw) / GT_수
```

값이 높을수록 좋으며, 음수도 가능하다(오차가 GT보다 많을 때). Ground truth 라벨이 필요하다.

---

#### 16.3.5 IDF1 (ID F1 Score)

**추적기가 동일인에게 얼마나 일관되게 같은 ID를 부여했는가를 F1으로 표현한 지표.**

MOTA는 탐지 정확도에 민감하고, IDF1은 ID 연속성에 민감하다. Re-ID와 결합된 파이프라인에서는 IDF1이 더 직관적인 성능 지표다.

---

#### 16.3.6 오라클(Oracle) 실험

**한 단계를 완벽한 정답(Ground Truth)으로 대체해, 해당 단계의 오차 기여분을 격리 측정하는 실험 방법.**

예: "Oracle YOLO + 실제 ByteTrack + 실제 Re-ID"로 실행하면, YOLO 오차가 없을 때의 Rank-1을 측정할 수 있다. 실제 전체 파이프라인과의 차이가 YOLO 오차의 Rank-1 기여분이다.

---

#### 16.3.7 오차 예산 (Error Budget)

**최종 목표를 달성하기 위해 각 단계에 허용할 수 있는 최대 오차율을 역산해 배분한 것.**

최종 목표(Rank-1 80%)에서 출발해 각 단계의 허용 오차를 계산하고, 현재 수치와 비교해 개선이 가장 급한 단계를 찾는 데 사용한다. (§15.4 참조)

---

#### 16.3.8 오차 귀인 (Error Attribution)

**최종 성능 저하의 원인이 어느 단계(YOLO·Tracker·Re-ID)에 있는지 분리·식별하는 분석 과정.**

귀인 없이 개선을 시작하면 병목이 아닌 단계를 최적화하는 시간 낭비가 발생한다. 단독 측정·오라클 실험·proxy 진단을 조합해 수행한다. (§15.3 참조)
